# 混合部署搬迁方案

状态：方案已确定，游戏后端已完成 ECS 内部测试；主域名和线上音乐尚未切换。备案仍在申请。本文是分阶段实施清单，不代表所有步骤已完成。

## 最终分工

| 入口 | 目标 | 职责 |
| --- | --- | --- |
| `wenyihao.cn` | 成都 ECS，Cloudflare 仅 DNS | 首页、GitHub 页、B站页、游戏页面、留言板 |
| `wenyihao.cn/realtime/*` | ECS 上的游戏后端 | 三款联机游戏共用唯一的房间后端 |
| `music.wenyihao.cn/music/` | Cloudflare 现有主 Worker 和音乐 Worker | 音乐页面、歌单、封面、登录、解析和音频流式中转 |
| `wenyihao.cn/music/` | 返回跳转到音乐子域名 | 仅返回跳转，不代理音乐页面或音频 |
| `/photos`、`/photos/*` | 暂不提供 | 照片墙继续下线，源文件保留 |

音乐播放：浏览器 → Cloudflare → B站，音频数据不经过 ECS。

游戏联机：浏览器 → 成都 ECS，连接不经过 Cloudflare 代理。

Cloudflare 继续作为整域的 DNS 服务商。域名仍在原注册商续费，无需转移。主站 DNS 最终采用仅 DNS，音乐子域名使用 Worker Custom Domain；不能把音乐子域名也指向 ECS。

这能让音频中转不消耗 ECS 出站流量，但主站页面、游戏资源下载、联机消息和留言响应仍消耗 ECS 流量。Cloudflare 自身的套餐、调用量和服务条款也需关注，不能理解为所有流量均免费且无限。

## 为什么先把音乐整页留在 Cloudflare

目前播放器使用相对路径访问 `/api/music/*`，登录 Cookie 是绑定来源的 `__Host-` Cookie，会话加密也包含来源。让音乐页面和全部音乐接口位于同一来源，可以保留现有登录与播放结构，无需先引入跨域 Cookie、CORS 凭据和跨域媒体接口。

现有 `wenyihao-cn-music` 为私有服务，不能直接给它绑一个域名就替代完整音乐站。应由现有主 Worker 提供音乐页面、ASSETS 和会话支持，再通过服务绑定调用私有香港音乐 Worker。保留 Worker 名称、服务绑定和 `MUSIC_SESSION_KEY`。

主站 `/music/` 只跳转到新来源；禁止在 Nginx 或 Node 中把音乐音频反向代理回来，否则 ECS 仍会承担音频出站流量。

## 阶段一：备案期间准备，不改当前访问入口

已完成：

- ECS 的 SSH 密钥连接与 Node.js 24 环境。
- 三款游戏共用房间逻辑、文件持久化、systemd 专用用户服务。
- 三款游戏双人协议、麻将私密消息、断线接管和重启恢复测试。
- 游戏后端仅监听 `127.0.0.1:8788`，未开放公网。
- 照片墙线上关闭，音乐仍在 Cloudflare。
- 主站 `/admin/` 公开只读观测台、脱敏访客网络/城市、ECS 每分钟上报、1 GB 月度出站保护与微信通知，详见[服务器监控](server-monitor.md)。流量统计是网卡口径，不是云账单硬上限。

待实施：

1. 建立 ECS 网站运行入口，准备网页静态文件、GitHub 接口和留言接口。
2. 留言板建立新的持久化存储，不导入 Cloudflare 旧留言；保留校验、分页和防刷限制。
3. 准备 Nginx 静态服务、WebSocket 转发和 HTTPS 配置，先只监听回环地址，通过 SSH 隧道验收。
4. 音乐站增加新的来源支持：站内其他栏目链接返回主域名，音乐 API、歌单和页面资源继续同源。
5. 完善访问限速、游戏连接与消息速率限制、日志轮转和磁盘检查；将已部署的流量统计、告警和超额保护纳入正式网站验收。它们不等于云账单的精确硬上限。
6. 准备分别发布 Cloudflare 与 ECS 的流程；ECS 使用专用部署用户，不把当前 root 私钥放入仓库或 CI。

此阶段不把主域名指向 ECS，不开放网站公网入口，也不把未改造的 Worker 程序直接当作普通 Node 服务运行。

## 阶段二：先验收 Cloudflare 音乐新入口

1. 为现有主 Worker 增加 `music.wenyihao.cn` Custom Domain，同时暂时保留原入口；由 Cloudflare 管理该子域名的 DNS 和 HTTPS。
2. 在新来源测试歌单、封面、访客播放、扫码登录、音质、拖动进度、随机播放和退出登录。
3. 浏览器网络检查：音频请求的主机必须为音乐子域名，而不是 ECS。选择歌曲不能产生任何 ECS 音频中转请求。
4. 检查音乐页中的主页、GitHub、B站、游戏和留言导航均返回主域名，避免把用户带回 Cloudflare 的旧游戏房间。

来源变化会影响浏览器存储：原主域名的 B站登录 Cookie、喜欢和最近播放不会自动转移到音乐子域名。登录需要重新扫码；若要保留喜欢和最近播放，应先实现用户主动导出/导入，不能声称已自动保留。已发布歌单由项目提供，不受此限制。

## 阶段三：备案通过后统一切换主站

前提：备案状态已确认通过，ECS 本地验收及音乐新入口验收通过。

1. 部署主站的正式 HTTPS 与证书续期、反向代理、安全组规则；游戏进程端口保持仅本机，由 Nginx 转发 WebSocket。
2. 预先清理旧的浏览器镜像择优机制：发布关闭镜像的配置，并提供退役 Service Worker，清理本项目的路由缓存。需要验证已经访问过的浏览器，不只测试无痕窗口。
3. 主站实时连接只指向 ECS 的同源 `/realtime/*`。停止把 `rt` 或旧主站列为可选房间后端。
4. 同步修改仓库里的 Cloudflare routes 和构建流程，移除主域名的 Worker 绑定、保留音乐绑定。不能只在控制台删除：后续 Git 自动构建可能重新接管主域名。
5. 再将主域名改为指向 ECS 公网 IP 的 A 记录、仅 DNS。检查是否存在遗留 AAAA 记录导致部分浏览器访问另一个入口。变更前保存原始 DNS、路由和部署版本作为回退资料。
6. 切换时安排短暂游戏维护，避免旧长连接与新房间后端并行。DNS 传播期间新旧页面可能共存，不能保证每个用户同一秒完成切换。
7. 从实际访问网络验证首页、GitHub、B站、留言、音乐跳转、照片 404、双人游戏、延迟和流量来源。测试已有登录/旧缓存的浏览器和新浏览器。

**禁止两个独立房间存储混用。** 旧 Cloudflare 主域名和 rt 镜像共用 Durable Objects，原先择优不会分裂房间；ECS 保存另一份数据，直接混入旧候选会让玩家进入不同房间。

主域名的 Custom Domain、DNS 和旧路由有相互关联，必须按当时控制台/API 的实际记录核对后执行，不直接套用会覆盖其他 DNS 记录的脚本。

## 阶段四：自动更新、监控与回退

目标仍为修改代码 → 推送 GitHub → 自动发布，但产物分成两个目标：

- Cloudflare：音乐页面、歌单、封面/登录/音频接口、必要静态资源。
- ECS：主站静态文件、GitHub 和留言后端、游戏后端、Nginx 配置。

现有 `npm run deploy` 目前只部署 Cloudflare，不会更新 ECS。正式切换前须完成新的 ECS 发布流程和验证，避免误以为推送后两边都已更新。同一个发布目标不要同时由多个互相竞争的 CI 流程更新。

ECS 发布使用版本目录和健康检查，保留上一版本。留言和房间数据独立于程序目录并备份，回退代码不删除数据。停止公开网站不会停止云盘、实例等其他计费项。

如需将主站回退 Cloudflare：恢复仓库及控制台对应的路由和 DNS、统一恢复房间连接配置，发布关闭或更新的浏览器路由缓存。ECS 与 Cloudflare 的房间不能自动合并；必要时重新建房。新留言数据另行备份，不能让回退静默丢失。

## 当前需要用户做的事
